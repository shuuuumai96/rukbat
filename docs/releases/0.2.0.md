# Rukbat 0.2.0 preview — release notes draft

**Not yet released.** Target: November 14, 2026 (Japan time), subject to the
[release plan](0.2.0-plan.md) and completion of acceptance testing.

## Scope

This preview separates struct data from methods, allows void declarations without
return-type annotations, and fixes correctness issues in existing language features
and tooling. It remains an evaluation release; later
0.x releases may change source compatibility.

## Migrating from 0.1.0

[日本語の移行案内](../ja/releases/0.2.0-migration.md)

Move methods out of a struct and into one `impl` block in the same module.
Keep that block next to the struct. Field-only structs need no change.

Before (0.1.0):

```rukbat
struct Counter {
    value: int

    fn increment(): void {
        self.value = self.value + 1
    }
}
```

After (0.2.0):

```rukbat
struct Counter {
    value: int
}

impl Counter {
    fn increment() {
        self.value = self.value + 1
    }
}
```

`impl` is now reserved; rename identifiers using that spelling. Each struct may
have at most one impl, and imported or built-in types cannot be extended.
Method invocation and receiver mutation use the existing rules.

For functions and methods that return no value, omit `: void`: `fn save() { ... }`.
Explicit `: void` remains accepted for compatibility; `fmt` normalizes it to the
omitted form. Returning a value still requires `: Type`. The omission always means
void and never infers a type from `return` statements or the final expression.

**The explicit `: void` declaration form is supported only during 0.2.x and will
be removed in 0.3.0, together with its formatter conversion.** Run `rukbat fmt`
using 0.2.x before upgrading to 0.3.0. After removal, the old declaration form
will produce a syntax error. The compiler will still use void internally to
represent calls with no return value. `powershell<void>` will still discard
PowerShell output instead of receiving it as a Rukbat return value; failures
still raise Error. Void is not a type of value that can be stored in a variable
or field. See the [removal decision](0.2.0-plan.md#explicit-void-removal-in-030).

Calls must use parentheses: `counter.increment()` and `helper(value)`.
Braces are for struct literals, such as `Counter { value: 1 }`; accidentally
accepted brace calls are now rejected. The existing `while` keyword is also
consistently rejected in declarations and editor rename operations.

Some previously accepted programs will now report errors, including arrays
without an inferable element type and unsafe uses of nullable globals across
loops or method calls. Supply an explicit array type or check nullable values
at the point of use. Do not rely on previously accepted incorrect behavior.

Pin the compiler version, update sources, run `check` and application tests,
then rebuild and test generated scripts on the deployment host before replacing
them. Updating the compiler does not repair existing `.ps1` artifacts.

## Changes since 0.1.0

The source changes include:

- Treat omitted function/method return annotations as void and format declarations
  without `: void`, while continuing to accept the explicit form.
- Preserve typed JSON array values and nullable arrays at PowerShell boundaries.
- Preserve nullable-flow checks across loops and method paths.
- Keep process exit codes as signed 64-bit integers and preserve overflow errors
  when evaluating dictionary keys.
- Normalize imported values before native text, logging, and HTTP operations.
- Compare strings using ordinal, case-sensitive UTF-16 equality on both
  PowerShell hosts. Locale-sensitive equivalence must not be relied upon.
- Preserve nullable datetime comparisons in test assertions.
- Capture update receivers before evaluating values, preventing an append from
  overwriting a replacement value with an old array.
- Respect declaration visibility in editor completion, include input context in
  parsing errors, and continue directory formatting after enumeration errors.

This list describes changes in source; it is not evidence that final packages
have passed acceptance or that every change has been reproduced against 0.1.0 binaries.

## Verification and remaining work

Release-wide verification is in progress. Record dated results and remaining
conditions in the [acceptance record](0.2.0-acceptance.md).

Before publication, finish package and clean-machine acceptance, confirm the
tested commit, add asset names and SHA256SUMS, and replace this draft status with
the actual verification results and known limitations. Do not publish this draft
as a completed release.

## 0.1.0 maintenance

When 0.2.0 is published, 0.1.0 maintenance ends. Its existing tag and downloads
remain available for reproducibility. No routine 0.1.1 is planned; emergency
issues are handled according to the [release plan](0.2.0-plan.md#010-policy).
